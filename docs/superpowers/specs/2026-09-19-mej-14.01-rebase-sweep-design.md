## §2 Harness: resolve the Foundry 14 app directory

`tests/e2e/helpers/target.mjs` gains a pure helper and the v14 preset uses it:

```js
/**
 * Newest `FoundryVTT-Node-<major>.<build>` directory under `baseDir`, by
 * numeric build. `entries` is the directory listing (injectable for tests).
 * Returns null when nothing matches.
 */
export function newestFoundryApp(baseDir, major, entries)
```

- Matches names `^FoundryVTT-Node-${major}\.(\d+)$`; picks the highest build.
- Ties are impossible (names are unique); non-matching entries (zips, the
  `Data` dir, other majors) are ignored.
- The v14 preset's `FOUNDRY_APP` becomes
  `newestFoundryApp(~/FoundryVTT-14, 14, readdirSync(...)) ?? <old 14.365 path>`
  so a machine with no matching dir keeps today's behaviour. The v13 preset
  is unchanged (13.351 is the only install and its dir is stable).
- `FOUNDRY_APP` in the environment still overrides the preset.

Unit tests (`test/e2e-target.test.js`): picks 14.368 over 14.365 from a mixed
listing; ignores `FoundryVTT-Node-14.365.zip` and `FoundryVTT-Node-13.351`;
returns null on an empty listing; the existing "defaults to the v14 target"
assertion is updated to expect the resolved path (`app` asserted with
`expect.stringMatching(/FoundryVTT-Node-14\.\d+$/)`, the rest exact).

Live check: with Foundry stopped, run one small spec (`00-mej-api`) and
confirm global setup launches Foundry from the 14.368 dir itself.

## §5 Attribution and report

Baseline: 0.19.0 gate, 24 specs, 0 regressions, environmental failures
spec 01 (4 tests: dialog path), spec 15 test 5, spec 16 test 1, spec 09 (1
test); one-off flakes in 06 and 21. The 02-hub-timeline test 7 failure seen
on 2026-09-19 on both lines is carried in as "known, cause unknown".

Every failure in runs 1–3b is classed as exactly one of:

| Class | Rule |
|---|---|
| baseline | same spec and test as the 0.19.0 list, same symptom |
| flake | passes on one isolated rerun of that file |
| new, both lines | fails on runs 1 and 2 alike; attributed to Foundry 14.368, dnd5e 6.0.3 or the 14.01 merge by the failing stack frame (companion vs MEJ vs core vs system file) |
| stock-only | fails on run 2 or 3 but not run 1 → the companion depends on a fork fix; name the fork commit if identifiable |
| fork-only | fails on run 1 but not run 2 → regression in the 14.01 merge on the fork line |

The report is committed at
`docs/superpowers/triage/2026-09-19-mej-14.01-companion-sweep.md`: stack
versions, cleanup numbers, the matrix with pass/fail/skip counts per run, one
row per failure with class, evidence (first error line and frame), and a
recommended follow-up (companion spec, MEJ backlog item, or harness fix). No
code fix is applied inside this project; a companion defect becomes its own
sub-project (spec first), after which 0.19.3 is cut.
