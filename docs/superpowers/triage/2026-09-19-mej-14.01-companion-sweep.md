### Verdict

**Two actionable defects came out of this sweep.** The first has a first
stack frame in product code, and that code is MEJ's, not the companion's:
`10-secrets-hub:167` → MEJ 14.01's
`JournalEntrySheet._renderPageView` dereferences `sheet.element`
unconditionally (`TypeError: … reading 'removeAttribute'`), which the fork's
`08ffca5` already guards. Everything else the sweep found is either carried in
from the baseline (2 tests), or fails identically on the fork line *before* the
14.01 merge (11 more tests, by the A/B probe — so caused by the platform or by
the companion, not by 14.01), or is a `stock-only` failure that only appears
when the companion runs against a 14.01 without the fork's backlog fixes (9
further tests, fork commit not identified for any of them), or is the stock
gate's own failure and its cascade.

**The second is the stock gate's own failure, and it is the one that blocks
the CHANGELOG's original claim** — its component is not established. The
native-mode stock gate failed: on bare 14.01 the Hub's New Session button never opened the
standalone `SessionSheet` and no session document was created
(`13-stock-smoke:191`, with `:243`, `:263` and the three run-3b tests as its
cascade). Whether the fault is the companion's `onNewSession` or MEJ 14.01's
create path is **not established** — the test captures no console output at
that point, and no previous stock gate has run on this Foundry/dnd5e stack.
The blanket "verified on MEJ 14.01 — both stock (native mode) and with the
extension API" wording is therefore not supportable and has been rewritten in
`CHANGELOG.md` to state what was tested (api mode, with the failure counts) and
that native mode on 14.01 is not verified. `module.json`'s MEJ relationship has
had its `verified: "14.01"` withdrawn for the same reason — a Foundry
`verified` field tells installers the pairing was tested and works, and on this
stack the stock gate says it does not; the relationship's compatibility is
`{"minimum": "13.06"}` again.
